# firmware_production_v3 — Lead II כפול + RLD ייעודי

קושחת הייצור הבאה של אבטיפוס ה-ESP32 + ADS1293. **שינוי רגיסטרים בלבד — אפס שינוי
חומרה, והחיבורים הקיימים (שקע P1) לא זזים.**

| שקע | פין ADS1293 | אלקטרודה | ערוץ |
|---|---|---|---|
| P1 (קיים) | IN1 | RA | — (משותפת) |
| P1 (קיים) | IN2 | LA | CH1 = Lead I (`IN2−IN1`) — כמו v2 |
| P1 (קיים) | IN3 | LL#1 | CH2 = Lead II‑a (`IN3−IN1`) — כמו v2, זה מה שהאפליקציות מציירות |
| **P2 (חדש)** | IN4 | **LL#2** | **CH3 = Lead II‑b (`IN4−IN1`)** — עותק שני של אותו ליד |
| P2 | IN5 | פנוי | — |
| **P2 (חדש)** | IN6 | **RLD** | מונע, לא נמדד (`RLD_CN=0x06`) |

אלה אותם פינים ואותם ערכי `LOD_EN / CMDET_EN / RLD_CN / AFE_SHDN / CH_CNFG` של
preset 0 ב-`../XIAO_NRF52840`, שנקראו חזרה משבב חי. ההבדל היחיד: סדר הערוצים נשאר
כמו בייצור (Lead I ב-CH1, Lead II ב-CH2), כדי ששום דבר במורד הזרם לא ישתנה.

## מה משתנה ומה לא

| | v2 (צרוב היום) | v3 |
|---|---|---|
| שם BLE / service / characteristic ישן | `BeatAlign ECG`, ‏16×9B | **זהה לביט** |
| שורת CSV ב-Serial / SPP | `I,II,III,aVR,aVL,aVF,lod,count` | **זהה לביט** |
| characteristic חדש `beb5483f‑…` | — | 12×13B: ‏`i32 I, i32 II‑a, i32 II‑b, u8 lod` + בייט דגלים |
| RLD | רוכב על אלקטרודת LL (`IN3`) | אלקטרודה משלו (`IN6`) |
| LOD | IN1..IN3 + "תיקון" לדפוס ניתוק LL | IN1..IN4, כל ביט אומר מה שהוא אומר |

כל אפליקציה ישנה — כולל נקודת השחזור `restore-point-2026-09-18` — עובדת מול v3 בלי
לדעת שמשהו השתנה. אפליקציה חדשה נרשמת ל-characteristic החדש אם הוא קיים, ואחרת
נופלת לישן (כלומר עובדת גם מול v2). החוזה המלא: `CYPHIX_SHARED/src/ble/protocol.ts`.

## ⚠ v3 מחייבת את כבל P2

עם `RLD_CN=0x06`, גוף שאין עליו אלקטרודה ב-IN6 נשאר **בלי ייחוס common-mode בכלל** —
זה בדיוק ה"רעש הכבד" שנראה ב-HW_PLAYGROUND v0.1.1 כשהכבל השני לא היה מחובר. זו החלטה
מודעת (5 אלקטרודות חובה, בלי מעבר אוטומטי ל-RLD על IN3). הקושחה לא מעמידה פנים:
`RLDRAIL` / `CMOR` (רגיסטר `ERROR_MISC`, אומת מול ה-datasheet עמ' 55) שנמשכים חצי
שנייה מדליקים את `ECG3_FLAG_RLD_FAULT` בחבילה, והאפליקציות מתריעות.
אם LL#2 נופלת — ביט 3 ב-LOD, והמיזוג בדוח חוזר לבד לעותק היחיד.

## מצב אימות

- ✔ נבנה נקי (`espressif32@6.12.0`, ‏RAM 12.5%, ‏Flash 88.1%).
- ✔ **צרוב על האבטיפוס (2026-09-18, ‏v3.0.1)** דרך `tools/flash_and_verify.ps1`:
  כל הרגיסטרים נקראו חזרה מהשבב כמצופה (`FLEX_CH1..3 = 0x11/0x19/0x21`,
  ‏`RLD_CN=0x06`, ‏`CMDET_EN=LOD_EN=0x0F`, ‏`AFE_SHDN_CN=0x00`, ‏`CH_CNFG=0x70`);
  ה-characteristic הישן נשאר ‎146B‏ ו-LOD בשלושה ביטים; החדש ‎160B‏, ‏0 חבילות
  פגומות, ‏0 פערי seq, ‏MTU 185.
- ✔ **קצב הדגימה נמדד, לא הונח:** ‏320.06Hz לאורך 44 שניות לפי מונה הדגימות ב-USB
  **בזמן** שלקוח BLE רשום (ב-v3.0.0 זה היה 306–309Hz — ראה הסעיף הבא).
- ✘ **טרם נמדד על גוף.** כל הבדיקות היו בלי אלקטרודות (‏`lod=0x0F`, ‏`rld_fault=1` —
  התשובות הנכונות למצב הזה). איכות האות, התנהגות ה-RLD החדש ודגלי ה-LOD עם
  אלקטרודות אמיתיות — עדיין לא נראו.

## v3.0.1 — למה הדגימה היא task נפרד

עד v3.0.0 (וגם ב-v2) task אחד עשה הכול: חיכה ל-DRDY, קרא את ה-ADC, ואז פירמט CSV,
כתב ל-Serial/SPP וקרא ל-`setValue()/notify()`. ה-ADS1293 מחזיק רק את ההמרה
**האחרונה**, אז בכל פעם שחצי-הפלט רץ יותר מ-781µs (מחזור אחד של 1280Hz) המרה נדרסה
לפני שנקראה. שום דבר לא אבד ברדיו — ה-`seq` נשאר מושלם והאות נראה נקי — אבל זרם
ה-"320Hz" פשוט רץ **לאט**: כהמרה אחת לכל קריאת `notify()`.

| | בלי לקוח BLE | עם לקוח BLE רשום |
|---|---|---|
| v2 (דרך BLE בלבד, חלון 5 שניות, דיוק ‎±1%‎) | לא נמדד | ‎317.8Hz — תואם להמרה אבודה לכל `notify` (‎1/64 = 1.6%‎) |
| v3.0.0 | ‎320.2Hz | ‎**306–309Hz (‎4%‎-)** |
| v3.0.1 | ‎320.2Hz | ‎**320.06Hz** |

המשמעות של 4%: כל מרווח שהאפליקציה מודדת (QT, ‏PR, ‏RR) יוצא קצר ב-4% וכל דופק גבוה
ב-4%, בלי שום סימן חיצוני. v3.0.1 מעביר את DRDY → SPI → median → decimate ל-task
בעדיפות 20 על core 1 (ה-Bluetooth על core 0), שמעביר דגימות 320Hz גמורות ל-`loop()`
דרך תור של 128 דגימות. ל-SPI יש משתמש יחיד אחרי `setup()`, ולכן ה-task מופעל **אחרון**
ב-`setup()`. פורמטי החוטים (BLE ו-CSV) לא השתנו בביט.
